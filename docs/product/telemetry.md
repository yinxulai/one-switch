# 匿名使用统计

本文定义**默认关闭**的匿名使用统计：它回答「有多少人在用、用的哪个版本、在哪些地区、哪些功能真被用了」，且**不采集任何用户内容**。

隐私总原则见 [security-privacy.md](./security-privacy.md)；本文是该原则下唯一允许出站的非模型流量，其余非模型流量一律不出站。

> **状态：客户端上报已下线（2026-09）。**
>
> 在 apis（`apps/apis/` Worker）下游方案定稿前，**客户端（core / console / 设置项 / 引导同意步骤）的上报实现已整体移除**，应用不再产生任何出站统计流量。
>
> - **保留**：`packages/contracts/source/telemetry.ts`（契约层，客户端与 Worker 共用的唯一一份定义）与 `apps/apis/`（Worker 源码与配置）。
> - **移除**：`packages/core/source/telemetry/`、`packages/core/source/management/routes/operations/telemetry.ts`、`SettingsSchema` 的 `telemetryEnabled` / `telemetryEndpoint`、console 的预览卡片与引导同意步骤、以及相关 i18n 文案。
>
> 本文其余部分描述的是**目标设计**：它仍是重新落地时的规范来源，但当前仓库内已无对应客户端实现。重新落地前请先解决 §6 与 §8.3 记录的下游问题（真实 `session_id` / `engagement_time_msec` 语义、服务端会话拼接）。

## 1. 定位与边界

### 为什么要有它

本地工具最难回答的问题是「到底有没有人在用、用的是不是我以为的那个功能」。请求日志统计的是**用户自己的请求**，它回答不了跨用户的聚合问题。使用统计补的就是这一块。

### 与产品承诺的关系

[security-privacy.md](./security-privacy.md) 原文是「默认不上报任何遥测数据；如未来加入匿名统计，必须默认关闭并显式征得同意」。本文是该条款的落地：

- **默认关闭**：`telemetryEnabled` 默认 `false`，新装用户不产生任何一个字节的出站；
- **显式同意**：只由用户在引导页或设置页主动打开；
- **可随时关闭**：关掉即刻停止后续采集，不需要重启；
- **可自证**：设置页提供「预览即将发送的内容」，展示的是**本地队列里的真实报文**，不是另一份手写的说明文案。

### 为什么要经过自建端点

统计流量不直连第三方分析服务，而是**先到我们自己的一个端点**。直接好处是密钥不落在客户端、报文可以先校验再转发；真正长期的好处是**客户端里写死的只有一个自有域名**，后端用什么、数据存哪里、存多久全都可以换，而不需要用户更新。论证与约束在 §6。

### 与出站代理的关系

使用统计**永不走用户的出站代理设置**，见 [outbound-proxy.md](./outbound-proxy.md)「非目标」：那条规则不代理遥测流量。实现上它是一个独立的直连连接器，理由有两条：

1. 用户配的代理是为**模型请求**服务的，把统计流量混进去会让代理日志里出现他没预期的目标；
2. 统计上报是「尽力而为」的流量，不该因为用户代理配置错误就永久失败，也不该在用户排查代理问题时被当成干扰项。

### 开发档不上报

`development` 环境**永远不上报**，与开关无关。开发期产生的启动次数会污染真实数据，而且开发档的数据目录（`.osw-development`）本来就是会被反复重置的。

## 2. 目标问题

首版只需回答六个问题。**这份清单就是需求边界**：不在表里的问题，首版不为其增加字段。

| # | 问题 | 观察单位 | 数据来源 |
|---|------|---------|--------|
| 1 | 用户趋势（活跃安装数随时间） | 去重安装 | GA4 |
| 2 | 地区分布 | 去重安装 | GA4 |
| 3 | 版本分布 | 去重安装 | GA4 |
| 4 | 语言分布 | 去重安装 | GA4 |
| 5 | 平台构成（系统 + 架构） | 去重安装 | GA4 |
| 6 | 功能使用排行 | 事件次数 | GA4 |

**首版只有 GA4 一层，我们不自己存一份。** 「去重安装」是一个安装标识的去重计数，不是自然人的数量（见 §4）。首版不做自建存储的取舍见 §8。

## 3. 红线：绝不采集

以下内容**任何情况下都不出站**，不因开关、不因调试模式、不因错误上报而例外：

| 类别 | 具体项 |
|------|--------|
| 请求内容 | 请求体、响应体、提示词、文件内容、模型输出、SSE 帧 |
| 凭据 | API Key、Authorization、Cookie、Set-Cookie、代理账号密码、密钥环条目 |
| 供应商标识 | Provider 名称、ProviderModel 名称、**baseUrl / 端点地址**、供应商包内容 |
| 本机标识 | 用户名、主机名、机器 ID、MAC 地址、数据目录路径、文件名 |
| 请求标识 | `requestId`、`attemptId`、逻辑模型 ID、工作流图 ID、改写规则 ID |
| 内容规模 | Token 用量、请求耗时、错误原文——它们是**用户的业务数据**，不是产品使用统计 |
| 精确位置 | 客户端不得上报任何地理信息；地区由服务端按**客户端真实 IP** 交给下游解析，见 §7 |

供应商 baseUrl 单独强调一次：用户自建中转的地址本身就是敏感信息，泄露它是实打实的隐私事故。因此事件属性里**不存在**任何自由文本字段——所有属性都是固定枚举或数值分桶（见 §5.3），没有地方能塞进去一个 URL。

## 4. 安装标识

### 本地标识

首次启用统计时在数据目录生成一个随机 UUID v4，写入 `telemetry-id`（权限 `0600`），与 `instance.lock`、`secrets.json` 同级。**不写进配置数据库**：它不该跟着用户配置一起被导出、备份或进供应商包。

删掉这个文件的下一个行为是「换了一台新设备」——这是正确语义，也是用户重置身份的现成手段。

### 上报的就是这个标识

上报时直接把本地 UUID 当 `installId` 发出，**不派生、不轮换**：

- 格式就是标准 UUID v4，因此 Worker 可以直接拿它当 GA4 的 `client_id` 用（GA4 要求 `client_id` 是 UUID 形状）。客户端不需要知道下游是 GA；
- **长期稳定**，所以 GA4 的 `users` 指标就是它的去重计数，跨天的活跃、留存、多日累计全部现成可用；
- 服务端不持有任何可与真人对应的映射，也没有第二份标识。

**取舍是明确的：标识长期稳定，意味着 GA4 里同一台设备是可关联的。** 换来的是跨天分析全部现成，且客户端里少掉一整套派生逻辑。首版接受这个取舍，理由有三条：

1. 标识本身不与任何个人信息相关——没有账号、没有邮箱、没有设备指纹，删掉 `telemetry-id` 即换新身份；
2. 统计默认关闭（§13），只有显式同意的用户才会有这个标识；
3. **轮换换不到真正的匿名，却会把 GA 的留存报表全部废掉。** 按天轮换意味着 GA 里每天都出现一批「新用户」，留存、漏斗、活跃全都失去意义；而 GA4 本来就是一个长期保留标识的系统，轮换只是把「我们手里不可关联」换成「GA 手里可关联但报表不可用」，净亏。

### 已知的取舍

同一台机器上的多个用户、多个数据目录，会被算成多个安装。本地工具没有可靠的「人」的概念，也不该为了统计去引入一个；**安装数就是安装数**，不假装它是用户数。

## 5. 事件模型

### 5.1 白名单

事件名与属性名都是**闭集**，定义在 `packages/contracts/source/telemetry.ts`，客户端、Worker、文档三处引用同一份定义。不在闭集里的事件名或属性名**在 Worker 侧被丢弃**，不是警告、不是降级，而是丢弃——这样客户端误传 `baseUrl` 之类的字段时，它在服务端进不了库。

### 5.2 公共字段

每条事件都带这些字段，由客户端填写：

| 字段 | 含义 | 约束 |
|------|------|------|
| `name` | 事件名 | 见 §5.3 |
| `occurredAt` | 事件发生时间（本地时钟的毫秒时间戳） | 服务端会按接收时间二次校验合理性 |
| `installId` | 本机匿名安装标识 | UUID v4 形状，不派生、不轮换 |
| `version` | 应用版本 | 由宿主注入，见 §12 |
| `os` | `win32` / `darwin` / `linux` | 枚举 |
| `arch` | `x64` / `arm64` / `ia32` | 枚举 |
| `locale` | `en` / `zh-CN` | 枚举，取用户实际界面语言，非系统语言 |
| `runtime` | `desktop` / `cli` | 枚举 |

这些字段**并不都作为事件参数发出去**：其中几个会落进 GA 的专用位置（用户属性、`device`、`client_id`），去向表见 §7。客户端只负责填值，不关心它落在哪——那是「客户端不感知 GA」的一部分（§6）。

### 5.3 事件目录（首版）

| 事件名 | 触发时机 | 属性 |
|--------|---------|------|
| `app_started` | 服务启动完成 | — |
| `service_start_failed` | 启动最终失败 | `reason`: `instance_lock` / `port` / `database` / `other` |
| `telemetry_toggled` | 用户改变统计开关 | `enabled`: `true` / `false` |
| `onboarding_finished` | 引导走完或跳过 | `skipped`: `true` / `false` |
| `route_mode_changed` | 生效模式切换 | `mode`: `workflow` / `rules` |
| `provider_created` | 新建 Provider | `kind`: `builtin` / `custom` |
| `model_added` | 添加 ProviderModel | `protocol`: `openai-completions` / `openai-responses` / `anthropic-messages` |
| `provider_test_run` | 连接测试 | `result`: `success` / `failed` |
| `rewrite_rule_created` | 新建请求改写规则 | — |
| `protocol_conversion_used` | 一次请求发生协议转换 | `from` / `to`: 同上三值协议枚举 |
| `failover_happened` | 一次请求发生故障转移 | `attempts`: `2` / `3` / `4+` |
| `workflow_node_run` | 工作流节点执行 | `nodeKind`: 节点类型枚举 |
| `logs_exported` | 导出日志 | `withContent`: `true` / `false` |

约束与说明：

- 事件名与属性名只能包含字母、数字与下划线，且都以字母开头；长度不超过 40 字符（GA4 的上限）。属性值不超过 100 字符；每事件属性数不超过 25 个。这些在 `telemetry.ts` 的类型里就卡住，不指望下游报错——GA4 对非法参数**不报错**，只是丢掉。
- `protocol_conversion_used` 只发「发生了转换」与两侧协议。协议是产品能力维度（三值枚举），不是供应商标识。
- `failover_happened` 的 `attempts` 分桶，不发精确次数：精确值对产品决策没有额外信息量，却是更细的行为指纹。
- **`workflow_node_run` 的 `nodeKind` 是闭集。** 它复用 `packages/contracts/source/router/types.ts` 的 `WORKFLOW_NODE_KINDS`（一个运行期数组，不是又写一份字面量联合），所以工作流引擎新增一种节点时，统计侧要么跟着认它、要么在改契约时一起决定，不会惄惄地开始丢事件。
- 事件目录**只增不删**：删掉一个事件名等于历史数据里那一列失去解释。要停用就在文档里标「已停用」，代码里停止发送。
- **单批上限 25 条。** GA4 Measurement Protocol 一次请求最多接受 25 个事件，超出的部分**静默丢弃**。客户端默认批量远小于它（见 §12），25 是硬上限，Worker 对超长批次直接拒绝而不是截断——截断会静默改变统计口径。

### 5.4 事件不是日志

`app_started` 之类的统计事件**不进运行日志**，也不从运行日志推导。运行日志服务于排障（见 [observability.md](./observability.md)），它有请求 ID、耗时、错误码；统计事件服务于产品决策，它必须匿名、必须低基数。两套东西的字段要求正好相反，混在一起会同时污染两边。

## 6. 上报链路

```
桌面端 / 命令行
    │  POST /v1/track    批量、直连、不透传用户代理
    ▼
自建 Worker（只有这一层持有 GA 密钥）
    │  校验 → 削平白名单 → 补来源地址 → 限流
    ▼
GA4 Measurement Protocol（展示层，首版唯一的下游）
```

三条设计决定：

1. **客户端只连自己的域名。** 用户能审计的网络行为是「往哪里发、发了什么」，这两件事完全由我们控制。GA 的密钥只存在于 Worker 的 secret 里，不进二进制、不进设置、不进日志。
2. **端点恒定，后端可换。** 客户端里写死的只有一个自有域名，其余全在服务端：换分析后端、换存储方案、换数据驻留区域、甚至整站迁移，客户端一行都不用改。这一条比看上去重要得多——已经装在用户机器上的旧版本没有第二次机会，**发布出去的地址就是永久地址**。直连第三方分析服务做不到这一点：`google-analytics.com` 与 measurement id 一旦写进二进制，任何后端调整都只能指望用户升级，而愿意升级的用户恰恰是最不需要被照顾的那批。
3. **GA 是当前唯一的后端，不是唯一的选择。** 首版把复杂度压在一个下游上（理由见 §8），但「以后能不能加东西」不由今天的决定锁死：只要第 2 条的接口在，加自建存储、换后端都只动 Worker。**选 GA 的成本因此是可逆的。**

关于第 2 条的落地约束：

- 端点域名必须是**自有域名**，不能是 `workers.dev` 子域：前者可以随时换绑、可以挂 WAF 与限流规则、可以按需切换背后的 Worker；后者绑定在平台命名空间上，改名即作废。
- 服务端对客户端承诺的是**请求格式**，不是数据去向。格式版本化（见 §7），去向随意。
- 因此客户端**不感知** GA 的存在：没有 measurement id、没有 GA 特有字段、没有 `client_id` 这个名字。`installId` 只是「本次上报的匿名安装标识」，至于它在下游被当 `client_id` 用，是 Worker 的事。

## 7. Worker 的职责

四处，一处都不能省：

| 职责 | 做法 | 原因 |
|------|------|------|
| 严格校验 | 用 `telemetry.ts` 的 schema 解析，拒绝多余字段 | 客户端误传敏感字段时，服务端是最后一道闸门 |
| 白名单削平 | 只挑认识的字段写入下游 | 校验通过不等于该字段该被转发 |
| 补服务端字段 | 真实客户端 IP 作为 GA 的 `ip_override` 交出去，由 GA 解析地理位置；`os`、`locale` 与 `device.category` 补进 GA 的 `device`；`receivedAt` 取服务器时间 | 客户端上报地理位置等于让它做设备指纹；而 IP 地理库在 GA 那边，比我们在边缘临时算准 |
| 限流 | 按 `installId` 与来源 IP 哈希双维度 | 端点公开，必须假设会被人灌垃圾 |

限流的两个维度各自取自哪里，值得写明白：**来源 IP 取 `CF-Connecting-IP`**（Cloudflare 填的真实客户端 IP，客户端伪造不了），哈希后只当内存里一个键用；**刻意不回退到 `X-Forwarded-For`**（随便谁都能写）。拿不到就以 `null` 处理、**跳过这一维度**，而不是共用一个假键：跳过只是少了一层保护，共用假键会把全体用户塞进同一个桶里——那是一场自制的故障。

同一个地址在这条链路上出现两次，去处不同，所以分开说：**转发给 GA 的是原值**（`ip_override`，由 GA 解析地理位置，见下一条）；**留在 Worker 里的只有哈希**（限流键，不落地、不写日志、isolate 一死就没了）。日志里两者都没有。

**限流是「尽力而为」，不是安全边界。** 状态活在单个 isolate 的内存里（isolate 一多相当于上限放大），所以它只能挡住「一个客户端自己循环打」，真正的洪峰要在 Cloudflare 侧用 Rate limiting 规则 / WAF 接住（**这也是端点必须挂自有域名而不是 `workers.dev` 的原因之一**）。

补充说明：

- **只有一条路径：`POST /v1/track`，其余一律 404（`/` 也是）。** 刻意不给部署流水线留一个健康检查接口：这块域名上「只有一条路径」本身就是最强的信号，而部署之后真正要确认的只有「路由注册上了没有」——对 `GET /v1/track` 期待 **405** 就回答了它，那是一个只可能来自本 Worker 的答案（部署后手动 `curl -i` 一次即可）。一条只接受写入的接口没有安全的匿名读探针，与其为此开一个接口，不如让「方法不对」来证明「路径对了」。根路径也不占：它是这块域名上唯一「一看就知道该留给别的东西」的位置。
- **公共字段各去各的地方，而不是全塞成事件参数。** `version` 与 `arch` 走 GA 的 `user_properties`（用户属性），`os` 与 `locale` 走 `device`，`installId` 走 `client_id`，只有 `runtime` 与各事件自己的业务属性留在事件参数里。去向表写在 `telemetry.ts` 的 `TELEMETRY_FIELD_TARGETS` 里，Worker 按它分发，不在 `switch` 里各写一遍。走用户属性换来的是「一个安装在版本分布里只算一次」（升级不会让它同时出现在两行）；代价是**用户属性只保留最后一次的值**，所以「版本分布」读的是「截至报告期结束时的版本」，要看版本迁移只能靠事件参数（首版不做，见 §11）。`runtime` 因此**刻意留在事件参数里**：桌面端与命令行共用数据目录、因而共用安装标识，同一个安装会先后发出两种 `runtime`，做成用户属性只会让它按最后一次上报来回翻。
- **声明不用作个性化广告。** 发往 GA 的请求固定带 `consent: { ad_user_data: 'DENIED', ad_personalization: 'DENIED' }` 与 `non_personalized_ads: true`：这个媒体资源只做统计、不做广告画像，那就在协议层说清楚，而不是只写在文档里。
- **`device.category` 固定填 `desktop`。** GA 的 `device.category` 是给「桌面 / 平板 / 手机」用的，而我们的两种形态都是桌面软件；真正需要区分的 GUI 与命令行已由 `runtime` 表达，所以这里只填一个能让 GA 的原生设备报表有意义的常量。
- **不做客户端鉴权。** 桌面应用内嵌的任何 token 都能被解出来，加了只提供虚假的安全感。防护靠「只接受白名单字段 + 限流」。
- **不接受客户端声明的地区**：客户端报文里根本没有这个字段，请求体里若出现 `country` 会被严格校验直接打回。位置是**服务端知道的那个事实**（连接来自哪个地址），不是客户端自述。
- **GA 侧的 `client_id` 用 `installId`，不用自定义维度。** GA4 自定义维度每天每维度约 500 个不同值后会把余下的折进 `(other)`，安装量级第一天就会被折叠；而 `client_id` 没有这个上限，GA 的 `users` 指标就是数它的去重。
- **必须显式告诉 GA 地理位置，而这个位置由 IP 推出。** 发往 GA 的请求是从 Cloudflare 机房发出的，若不提供位置信息，GA 会按**机房 IP** 定位，结果是「所有用户都在数据中心所在地」。因此 Worker 把 `CF-Connecting-IP`（Cloudflare 填的**真实客户端 IP**，客户端伪造不了）作为 GA 的 **`ip_override`** 发出去，由 GA 自己的 IP 地理库解析成城市与地区。
  - **这是故意的选择**：IP 地理库在 GA 那边，比 Worker 里读一个只有国家级的 `cf.country` 准，而且客户端报的地理信息一个字都不可信——交给 GA 至少只依赖「连接的来源地址」这一个事实。
  - **代价必须承认：用户的 IP 会随这次转发进入 GA**（报文的其余部分仍是白名单字段）。这是本项目唯一一处把地址交给第三方的行为。
  - **报文中不能出现 `user_location`**：GA 官方参考文档写明 `user_location` 优先于 `ip_override`，两者同时发送时 `ip_override` 会被忽略，等于白传（位置还会退回到按机房出口算）。两者只能给一个，这里给的是 IP。
  - 拿不到地址时**不传 `ip_override`**，而不是编一个：编一个会把用户定位到某个具体的地方，这比「不知道在哪」错得多。
  - 同一次请求里，这个地址还被算成**限流键**（哈希、不落地、不写日志，见下一条）。
- **补 `session_id` 与 `engagement_time_msec`，但只按它们的最小语义用。** 这两个不是客户端字段，是 Worker 给 GA 补上的。GA 官方参考文档写得很直白：不带这两个参数的事件「可能不会完全反映在实时用户数中」，而实时报告正是排查埋点时唯一的窗口（§10），所以它们不是可选项。`session_id` 取**服务端收到时刻的自然日编号**——一次使用日算一个会话，是 `^\d+$` 的正整数，同一批同值、跨天自然翻新；`engagement_time_msec` 给一个固定的非零小值，只为让这批事件被计入「互动」。**代价要承认**：这样得到的「会话数」等于「有上报的安装·天」，是个下界而不是真实的会话切分；「平均互动时长」是那个常量的算术结果，**没有意义，不要读**。用服务端时刻而不是客户端时刻，是为了让改系统时间伪造不出会话。
- **避开 GA 的预留名。** `error`、`session_start`、`first_visit`、`app_install`、`app_update`、`user_engagement` 等事件名不能用；参数名不得以 `_`、`firebase_`、`ga_`、`google_`、`gtag.` 开头。事件目录（§5.3）已按此约束取名，新增时要再查一次。
- **时间戳只回溯 72 小时。** GA4 拒绝更早的 `timestamp_micros`。因此 `occurredAt` 超出回溯窗口时**丢弃该字段而不是丢弃事件**，让 GA 用接收时间——补报本来就允许丢失（§12）。
- **带字符集前缀的 `Content-Type` 才算 JSON。** `application/json; charset=utf-8` 接受，`text/plain` 一律 415。
- **请求格式版本化，服务端长期保留旧解析。** 端点不变意味着会有很旧的客户端一直打过来，所以新增字段必须可选，破坏性变更开新路径（`/v2/track`）并保留旧路径。这与「自有域名不可变」是同一件事的两面：既然后端可以换，老客户端就永远不会下线，那么兼容窗口就不是「支持几个版本」而是「永久」。

## 8. 数据存哪与保留期

**首版只有 GA4 一份，我们不自己存副本。** 三个原因：

1. 六个视图 GA 开箱即用（§2）；
2. 自建那一层的全部价值是「回答 GA 答不了的问题」，而首版还没有这类问题；
3. 不存就不会丢，也不用维护一份带标识的数据。

### 8.1 保留期的天花板

GA4 标准媒体资源的事件数据保留 **14 个月**（用户级数据的保留期可配 2 或 14 个月）。因此：

- **首版能看的最长趋势是 14 个月**，更早的数据取不回来；
- 年度趋势、同比、跨版本对比都在这个窗口内，够用——这也是「14 个月」可以被接受的全部理由；
- 想突破这个窗口只有一个正确入口：**开启 GA 的 BigQuery Export**。开启之后的数据永久留在自己的 GCP 项目里，可任意写 SQL。这是「需要时再买保险」，比提前自建一套汇总便宜得多，且不需要现在做决定。

### 8.2 什么时候才加自建存储

出现下面任意一条时，加一层自有的汇总存储：

- 需要 14 个月之外的固定报表，又不想养 BigQuery；
- 需要 GA 答不了的口径（自定义交叉、超大基数去重）；
- 需要「统计不依赖第三方账号」的可控性。

**加它的成本已经预付了**：客户端一行都不用改（§6 第 2 条）。届时最小形态是在 Worker 里加一个 Analytics Engine 写入 + 一个每日汇总任务——它与现在要写的 Worker 是同一个部署单元，所以增量成本只是 Worker 里的两个文件。

### 8.3 明确不做的事

- **不做原始事件归档**（R2 / 对象存储）。一旦需要长期分析，正确的第一步是开 BigQuery Export，那是 GA 官方的原始数据出口；自己再存一份原始事件只是多一处带标识的长期数据，收益重复；
- **不建汇总表、不写查询脚本**：它们是 §8.2 那种需求出现之后的产物，不是现在的产物。

## 9. GA4 的能力边界

选 GA 是拿它的现成界面，但它的边界必须写在文档里，避免以后误以为「GA 上没有就是没有」：

| 边界 | 后果 | 我们的应对 |
|------|------|-----------|
| 自定义维度基数上限 | 安装级维度不可用 | 安装标识走 `client_id`（§7） |
| 事件数据保留 14 个月 | 做不了更长的趋势 | 接受；需要时开 BigQuery Export（§8.1） |
| 标准报表延迟 24–48 小时 | 埋点出错要等一天才发现 | 用实时报告（Realtime）当场看事件有没有到（§10） |
| 维度必须事先注册 | 事后想加的维度，历史数据里是空的 | 上线前把版本与架构**两个用户属性**注册成用户级自定义维度（§11） |
| 数据模型是会话 / 页面 | 「安装级分布」要靠硬塞；会话指标天然失真 | 口径在 §11 写死；会话参数按最小语义补发（§7），会话类报表一律不读 |
| 不带 `session_id` / `engagement_time_msec` 的事件可能不计入实时用户数 | 埋点「看起来没生效」，实际是 GA 没归属 | Worker 统一补这两个参数（§7） |
| 原始数据出口只有 BigQuery Export | 深入分析要养一个 GCP 项目 | 接受，需要时才开（§8.1） |
| 非法参数静默失败 | 静默丢数据，且返回 204 看不出来 | 类型层卡死长度与枚举（§5.3） |

**判断规则：GA 上没有的答案，要么是维度没注册，要么是超出了 14 个月。** 先查这两件事，不要因为界面上看不到就认为数据没采集。

## 10. 查询与分析

首版只有 GA 界面一个入口：六个视图在「报告」里现成，临时提问用「探索」（Explorations）自己拼，不需要写代码。

**不自建看板。** 六个视图 GA 已经画好，而临时提问用探索报告比维护一个界面更快。真要出固定看板，那属于 §8.2 的自建存储需求——先有需求，再有界面。

**也不自建查询脚本。** 只有在开了 BigQuery Export（§8.1）之后，才有「本地写 SQL 查原始数据」这件事；到那时脚本与凭证再一起设计，现在写等于为一个还不存在的表设计接口。

本地开发想验证埋点是否到达 GA，用实时报告即可（前提是 `telemetryEndpoint` 指向本地 Worker）——注意实时报告能显示用户数，靠的正是 §7 里补的那两个会话参数。GA 对非法参数**不报错**（§9），所以「事件到了但参数少了」这类问题在实时报告里看不出来，只能回到协定层查：`telemetry.ts` 里的长度与枚举约束，以及 Worker 报回的 `invalid_payload.issues`。

## 11. 分析口径

六个视图在 GA 里的指标与维度，**优先用 GA 的原生字段，只有 GA 没有对应项的才注册自定义维度**：

| 视图 | 指标 | 维度 | 维度来源 |
|------|------|------|---------|
| 用户趋势 | 用户数 | 日期 | 原生 |
| 地区分布 | 用户数 | 国家 | 原生（Worker 发 `ip_override`，GA 自己按 IP 解析） |
| 版本分布 | 用户数 | 应用版本 | **用户属性 `version`** |
| 语言分布 | 用户数 | 语言 | 原生（来自 `device.language`） |
| 平台构成 | 用户数 | 操作系统 + 架构 | 操作系统原生（来自 `device.operating_system`）；架构为**用户属性 `arch`** |
| 功能使用排行 | 事件数 | 事件名称 | 原生 |

口径说明：

- **「用户数」就是去重安装数。** GA 按 `client_id` 去重，而 `client_id` 就是 `installId`（§4），所以它等于「这段时间内有几个安装上报过」。GA 界面里它叫「用户」，语义上不要读成自然人；
- **只有两个自定义维度需要注册：`version` 与 `arch`**，而且注册时是**用户级（user-scoped）**维度——因为这两个值在报文里走的是 GA 的 `user_properties`（§7）。这是最容易漏的一步：维度必须在**首次上报之前**注册，否则注册前的数据在这些维度上永远是空的，且无法回填（§9）。GA 对用户属性的值有 **36 字符**上限，超出会被静默丢弃，所以 `telemetry.ts` 直接按这个长度卡住了 `version`。两个维度的取值都是个位数到几十量级，远低于基数上限；
- **版本与架构读的是「最后一次的值」，不是「那天的值」。** 用户属性按用户保存，GA 记的是最近一次看到的值，所以「版本分布」的正确读法是「截至报告期结束时各版本的安装数」。要知道一个安装**什么时候**换的版本，得有事件级的版本参数——首版不做（§15）；
- **绝不能把安装标识做成自定义维度**：它是超高基数，第一天就会被折进 `(other)`（所以它才走 `client_id`）；
- **事件计数用 GA 的「事件数」**，它对应 §5.3 目录里每一行的触发次数，不做去重；
- **跨天的留存与活跃现成可用**：`installId` 不再轮换（§4），所以 GA 自带的活跃、留存、多日累计都是真实值，不需要我们额外做任何事；
- **不做跨视图的交叉**（例如「某版本在某地区的人数」）：那需要自定义维度组合或探索报告。首版不做，出现需求时按 §8.2 走。

## 12. 运行时行为

### 队列与批量

- 事件先入**内存队列**，按 `批量条数` 或 `间隔` 触发发送，先到先发；
- 内存队列**不落盘**：进程退出时未发出的统计事件直接丢弃。统计不是业务数据，为它写一份磁盘队列等于给用户留一份额外痕迹；
- **失败静默**：网络错误、超时、非 2xx 一律丢批次，不重试、不弹窗、不写运行日志的 `error` 级别（最多 `debug` 一行）；
- **超时短**：单次上报超时按秒级设置，不参与任何重试预算；
- **不阻塞启动**：上报循环在监听成功后启动；`app_started` 也走同一条队列。

**统计允许丢失。** 上面这几条合起来的意思是：断网期间的启动不会被补报、闪退前的最后一个批次会消失、手动关闭统计后的那个事件可能发不出去。这不是缺陷：统计数据的用途是看趋势与量级，为它加上持久化队列、重试预算与补报机制，得到的是一份用户机器上的额外痕迹和一套跟业务数据同等复杂的可靠性要求，而这两样都不是它该有的。

**批量大小的两个约束。** 默认批量取十几条量级，它同时受两个上限约束：单批不得超过 §5.3 的 25 条硬上限，也不能让一次上报明显拖慢关闭流程。25 这条必须由客户端自己守住，因为 GA4 对超出的部分**不报错、直接丢**。两个约束都不是性能调优，而是「小批量、允许多发几次」这个取向的边界。

### 版本号来源

core 是纯 Node 进程，拿不到渲染层的 `__APP_VERSION__`，也没有 `electron`。因此**版本号由宿主注入**，随启动参数一起传进 core，core 不自己解析版本、不读 `package.json`：

- 桌面形态：主进程用 `app.getVersion()`；
- 命令行形态：cli 宿主自行解析。

### 采集与保留

- 关闭开关**只影响后续采集**，不删除已经上报到 GA 的数据。GA 提供按 `client_id` 删除数据的流程，而用户能拿出的凭据就是他的 `installId`（设置页的预览里能看到它）——这也让「我的数据」有一个可指认的对应物；
- 本地只有 `telemetry-id` 一个文件，删掉即等于换新设备。旧标识在 GA 里的记录不再产生新事件，14 个月后自然过期。

## 13. 设置与同意

新增两个设置项（`SettingsSchema`）：

| 字段 | 类型 | 默认 | 语义 |
|------|------|------|------|
| `telemetryEnabled` | boolean | `false` | 是否上报匿名使用统计 |
| `telemetryEndpoint` | string | 空 | 保留字段，见下 |

**关于端点是否可配。** 端点写死在 `telemetry.ts` 的常量里，**不暴露给用户设置**：一个「改上报地址」的输入框既是无用的自由度（用户没有别的接收端），又是一个把统计流量导向他处的口子。`telemetryEndpoint` 仅作为开发档覆盖（指向本地 Worker），正式构建下为空即用常量。

设置页要求：

- 开关所在卡片必须写明**发什么、发给谁、怎么关**，不能只有一个标签；
- 提供「预览即将发送的内容」，渲染本地队列里的真实报文；
- 开关与预览必须同屏，说明和开关之间不能隔一次跳转。

同意入口有两个，指向同一个设置项：

- **引导页**：在走完流程前问一次，默认不勾选。跳过引导不等于同意，跳过时该字段保持 `false`；
- **设置页**：随时可改。这是唯一能让用户关掉它的地方，所以它必须存在且可达。

**关闭时尽力发一次 `telemetry_toggled`。** 关掉之后就不再采集，所以这一次是最后一次机会；能发出去就发，发不出去就丢。没有它，我们只能看到「某个安装从某天起不再出现」，而这既可能是关了统计，也可能是卸载或断网——区分不了就等于没这条数据。

界面文案进 UI 语言目录，与 [i18n.md](./i18n.md) 的三层模型一致；设置页布局遵循既有的「一行一条」约定。

## 15. 非目标

- 首版不自己存一份统计：不建原始层、不建汇总表、不做归档（§8.3），只保留 GA 一份；
- 不自建看板与查询脚本（§10）；
- 不做崩溃与异常上报：它的脱敏要求、保留期、采样策略与使用统计完全不同，混在一起会同时破坏两边（要做得单独设计）；
- 不上报请求级指标（耗时、Token、状态码）：那是用户自己的业务数据，已在本地观测里完整存在；
- 不做 A/B 实验与远程开关；
- 不采集任何自由文本；
- 不因统计失败影响任何用户可见行为。
