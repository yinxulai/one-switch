# 桌面端产品形态

## 技术栈

Electron + Node + TypeScript + React/Vite，选型理由与版本要求见 [tech-architecture.md](./tech-architecture.md)。

## 主要入口

### 菜单栏 / 托盘

- **macOS**：菜单栏图标
- **Windows**：系统托盘图标
- **Linux**：系统托盘（P1 完善）

### 菜单快捷区

托盘菜单结构固定为三组，不随状态增删条目：

1. **代理服务**
   - 状态行：`运行中 · <端口>` / `已停止`（不可点击，它说明下面那组操作的对象是什么）
   - 复制接入地址：子菜单按客户端类型列出两个 Base URL（`OpenAI · <origin>/v1`、`Anthropic · <origin>`），点一条复制一条
   - 启动 / 停止代理服务：一个条目按当前状态切换文案，文案本身就是动作
2. **打开主界面**
3. **退出 OSW**

macOS 会额外渲染一个原生分组标题「代理服务」（Electron 的 `type: 'header'`，macOS 14+ 才支持）；
其他平台没有标题语义，只用分隔线分组。

菜单栏 / 托盘只提供上述基础操作，逻辑模型、供应商和监听配置统一在主界面管理。

在 macOS 上关闭主窗口不会退出应用：代理和菜单栏图标继续运行，同时隐藏 Dock 图标；从菜单栏重新打开主界面时恢复 Dock 图标。

### 图标状态

**图标不表达状态**：所有平台、所有运行状态共用同一张单色图标（macOS 走 template image，由系统按菜单栏明暗自动着色；
Windows / Linux 为白色），状态由菜单第一行与鼠标悬停提示表达。

不用颜色当状态通道的原因：macOS 的 template image 由系统接管着色，应用提供的彩色不会被采用；
Windows / Linux 的托盘底色随系统主题变化，彩色图标在浅色底上会糊成一团。
而菜单第一行能直接写出端口号，比一个色点准确。

### 逻辑模型页

管理每个逻辑模型的自动切换候选列表，每个列表项是一个 ProviderModel：

- 逻辑模型卡片（名称、说明、内建默认标识）与新增 / 改名 / 改说明 / 软删除逻辑模型；改名与删除落在卡片头右侧、与第一行同高的一排幽灵按钮上，按钮与名称同行，hover 或键盘聚焦才浮现。这排按钮**不铺自己的底色**：它出现时右侧的切换器会同时让出同样宽的位置，按钮下面是空出来的卡片底，再盖一层渐变或模糊只会显出半透明的一块脏色（模型行上的遮罩则相反——它压在供应商链接、指标与状态徽标之上，非模糊不可）
- 模型列表（协议类型、远端 URL、Provider API 模型名、Provider、优先级、启用状态、ProviderModel 健康状态）
- **当前使用标识**：高亮显示当前正在使用的列表项
- 新增 / 编辑 / 删除列表项；「添加模型」是候选列表末尾多出来的一行（同宽、同左内边距、hover 才浮出底色，比模型行矮一档），不是卡片头上的按钮——它是候选列表的下一行，而不是这张卡的头等操作。这一列的行本身没有边框、只用发丝线分格，所以它也不做虚线框：那样会在这里多出第三种形状（尺寸取自路由规则「再加一条」，但那处的条件行本来就是盒子，虚线才成网格）
- 卡片内容是**整块通栏**的：列表、空状态、末尾的「添加模型」都贴到左右边缘，只在卡片头保留内边距。因此卡片底部不留内边距——这一行直接与卡片下边缘齐平，否则列表走完后会在末尾多出一条既没有发丝线收尾、也不属于任何一行的空白带
- 拖拽调整候选顺序（优先级）
- 顶部指标卡汇总该逻辑模型的关键指标（请求成功率、平均响应耗时、平均 TPS、当前可用模型）。每张卡只有「标签 + 数值」两行：口径说明压在标签右侧的 info 图标上，悬停或聚焦才展开，不铺成第三行小字——四张卡里只有算得复杂的指标写得出口径，摆在一起就是两行与三行参差，还把「看一个数」变成「读一句话」。缺数据时数值位照旧占位（用 `—`），不因为没数据就换一种版式

> 内建默认逻辑模型 `default` 是未命中任何逻辑模型时的落点，因此它的名称不可改、也不提供删除入口（说明仍可编辑）；其余逻辑模型可自由创建、改名与软删除。软删除只打 `deletedTime` 时间戳，历史请求日志、调度绑定与路由图落点仍按 ID 引用得到它。详见 [data-model.md](./data-model.md)。

### 模型管理页

- Provider 列表（名称、状态、连续失败、冷却状态）
- 新增 / 编辑 / 删除 / 启用禁用 Provider，并管理其下的 ProviderModel 与端点绑定
- 配置空闲超时时间（两次数据间隔，流式不超时）
- 连通性测试：复用真实模型请求链路验证密钥与端点
- 导入 / 导出供应商包：单个供应商详情可导出，列表页可导入或导出全部；导入前展示包内供应商、将被覆盖的同名供应商数量和明文 API Key 条数，详见 [provider-model.md](./provider-model.md)

### 请求记录页

- 最近请求列表（状态、时间、逻辑模型、协议、传输形态、输入 / 缓存 / 输出 Token、TTFT、TPS；列口径见 [observability.md](./observability.md)）
- 查看某次请求的详细尝试过程（每个候选 ProviderModel 的结果）
- 查看完整客户端请求/响应和每次 Provider 尝试内容
- 有协议转换时查看转换前后的请求/响应内容
- 使用抽屉或对话框打开详情，支持格式化、复制和折叠
- 筛选：按模型、协议、供应商、状态、时间范围
- 日志字段、采集开关与保留策略见 [observability.md](./observability.md) 与 [data-model.md](./data-model.md)

### 接入配置页

这一页是本机服务的**说明书**，不是任何客户端的教程：它只写三个属于我们自己的事实——服务在哪条地址上、客户端要用的三个值是什么、服务接受哪些路径。页面上**不出现任何工具的名字**，措辞也不借第三方的：产品名、菜单路径、字段叫法都由别人定义、随时会变，追着它们更新等于把这一页的维护成本建在别人的排期上。反过来，任何客户端都能拿这三个事实对上号，用户从客户端连不上回来时，也只需要在这三个事实里找答案。

版面因此是单调的一列，顺序就是读的顺序——状态带 → 地址卡 → 接口表：

1. **地址卡**（`components/address-card.tsx`）：整页唯一的目的地，因为三个值里只有它会写错——它有两种写法（带不带 `/v1`），两种服务端都受理。所以页面上只出现**一条**地址，另一种写法降级成一句话说明：两条并列的地址只差一个 `/v1`，抄错行是这里最贵的错误。它是全页字号最大的东西。下面两行用同一种「左标题 + 说明、右值 + 复制按钮」的设置行摆出 API Key 与模型名，两个值旁边都是**同一种图标复制按钮**：同一个页面里出现两种复制按钮（一种带文字、一种只有图标），用户每遇到一个就得重新认一次，重要性该由值的字号承担而不是按钮的形状
   - API Key：本地不校验鉴权，转发时会被换成渠道自己的密钥，所以给一个固定值（`service-facts.ts` 里的 `sk-osw`）让用户照抄
   - 模型名：它**不是固定值**，而是路由的输入——任意非空模型名都受理，命中哪个逻辑模型、最终连到哪个上游都由路由决定；页面上给的 `default` 只是兜底那一个（引用契约层的 `BUILT_IN_DEFAULT_LOGICAL_MODEL_NAME`），即「不知道填什么就填它」
2. **接口表**（`components/interface-table-card.tsx`）：「本服务接受的接口」，每行一条路径——方法 + 主写法 + 等价写法 + 一句它是什么 + 协议名（只在本地应答的那条标「本地应答」）。表的内容全部来自契约层的 `PROXY_INTERFACE_ENTRIES`（`packages/contracts/source/protocols.ts`），**不在页面里维护第二份路径清单**：它由 `packages/core/source/proxy/protocols/interface-surface.test.ts` 双向守着——契约里写下的每条（方法，路径）都必须在真实注册表里解析成声明的协议，注册表里每条协议路径也必须在契约里出现。**只收真正支持的接口**：注册表认得出旧版文本补全与文本向量（与对话补全同属 `openai-completions`），但上游地址是按协议配的，它们的正文没有对应的地址形态，转发出去只会落到一个聊天接口的地址上——「认得出」与「支持得住」是两件事，清单只承诺后者。这些不受理但认得出的路径在内核测试里各自留了名字（`UNEXPOSED_ROUTES`），多出一条路径必须有人做一次决定
3. **收尾**只留一件事：怎么知道自己接上了——请求记录里出现这条请求就是接上了。这里**不摆示例命令**（那是「谁的写法」的问题，这一页不碰），也不拿本地的 `/v1/models` 冒充转发链路的验证（它只列出兜底模型名，不展开上游，表里因此标成「只列兜底模型」）

服务状态不带序号，摆在这条清单之上：它是这一页的**前提**（服务没跑，下面写什么都没用），不是这一页的内容，所以它是一条**状态带**而不是一张卡——状态点与状态字、监听地址（通配监听时另行说明其他设备也能连）、谁能连，右端是「修改监听地址」这个次要入口；启停按钮在页头。

监听 `0.0.0.0` 时它本身不是可访问地址，展示给客户端的一律回落到 `127.0.0.1`；状态带里显示的是原样的绑定地址，并在旁边说明其他设备也能连。服务没跑或地址不全时，地址位摆占位符并禁用复制，而不是整块消失——版面不跟着数据有无变形。

侧边栏、托盘子菜单与页头标题这一页都叫「接入配置」：这一页改的是「本服务对外长什么样」，不是「你该点哪个菜单」，所以名字不跟着谁的叫法走。

### 智能路由（路由工作台）

工作流图与规则表的编辑与试跑，页头标题后面跟一个模式切换器选当前生效的模式（同一时刻只有一种）：

- **工作流图**：节点图的编辑与试跑，产品口径、节点设计与默认策略见 [route-design.md](./route-design.md) §2–§4；
- **规则表**：从上往下匹配的规则清单，行上摆着名字、条件读法、落点与启停，改名与条件全在行内展开里改（输入带类型化提示语，落点是单选，逻辑模型在一个多选输入框里勾选、勾选顺序即优先级，再加一条条件是条件列末尾那个虚线空格子），排序只走拖拽，兜底落点单独一行、单独展开，新增规则是页头右上角的主按钮，语义见 [route-design.md](./route-design.md) §2.11。

两种模式各自一套正文、各自一个试运行抽屉——两个抽屉要回答的问题不同（图回答「这趟经过了哪些节点」，规则表回答「为什么是这一条」），因此文案与版面也各写各的。页头同样如此：标题写的就是当前模式的名字（工作流编排 / 路由规则），模式图标按钮跟在标题后面（点开的是那个全局的模式选择弹窗，设置页的「生效模式」是它的另一个入口），试运行按钮在两处叫同一个词。真正共用的不止页头版式与同一份示例请求：**保存按钮、保存弹窗与历史版本菜单在两个模式里也是同一套**（规则表的保存会把整张表发布成一个新版本、旧版可回滚，量词换成「几条规则」、说明文案换成规则表那一份）。图模型、控制流与持久化见 [workflow-engine.md](./workflow-engine.md)。

## 用户流程

### 首次使用

1. 启动应用，菜单栏/托盘出现图标
2. 引导添加第一个 Provider（名称、API Key、超时）
3. 在逻辑模型页添加模型（选择协议、填入远端 URL 和 Provider API 模型名、选择 Provider）
4. 可继续添加多个模型，拖拽调整顺序
5. 打开接入配置页，把页面上那条地址写进你用的客户端（带不带 `/v1` 都受理，页面上只说一条）
6. `model` 可保留客户端原有的任意非空值，代理会通过 `default` 逻辑模型处理，并在转发时替换为当前 ProviderModel 的 `modelName`；API Key 同理，填任意非空字符串即可
7. 从客户端发一条消息，在请求记录里看到这条请求就说明链路已通，控制台里显示尝试过程和切换路径

### 日常使用

1. 应用在后台运行，可选开机自启
2. 托盘菜单第一行与悬停提示反映代理是否在运行（图标本身不表达状态）
3. 临时禁用某个供应商或调整优先级
4. 查看请求日志了解每次请求经过了哪些供应商、在哪里失败、最终由谁成功

## 路由与工作台

路由工作台是代理策略本体的编辑入口：请求怎么被识别、怎么判定、落到哪个逻辑模型，全部表达为一份**可编辑且可版本化的定义**——工作流图或规则表，代理运行时执行的就是当前生效的那一版。这些内容各自只有一个权威落点，本文不再重复：

- **产品语义**（两种模式的划分与规则表语义、`route` 输出契约、路径取值与比较操作符、默认「模型直达」策略、四个策略预设）：见 [route-design.md](./route-design.md) §2
- **引擎与图模型**（节点/边结构、控制流与端口、迭代、脚本与 LLM 能力注入、图的加载与保存）：见 [workflow-engine.md](./workflow-engine.md)
- **画布交互与节点面板**：见 [route-workbench.md](./route-workbench.md)

契约以代码为准：图模型与节点定义在 `packages/contracts/source/router/types.ts`，落库结构在 `packages/core/source/database/config-schema.ts`（`workflows` 表在配置库里）。
